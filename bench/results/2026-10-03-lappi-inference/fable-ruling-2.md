**1c revisited — can the GPU compute v1-identical bytes faster?** No. v1 hashes each buffer sequentially; a GPU can give one buffer one thread. A single Metal thread does ≈2,000 scalar ops per 64-byte block → ~50 MB/s per thread [I]. Per digest: T=131, 18 × 1 MB buffers in parallel → ~20 ms (CPU 1a: ~5 ms soft, ~1.3 ms hw). 8K, 16.8 MB largest buffer → ~340 ms (CPU 1a: ~57 ms soft, ~14 ms hw). GPU loses by 4–6× at every T. The cheapest decisive measurement would be a one-thread SHA-256 Metal microbench — a tessl kernel in a tree ojas holds, and the arithmetic already closes it: **do not measure, do not build.** tessl has no SHA kernel to reuse: `rg -uu -il sha` over all 30 `kernels/*.metal` returned nothing [rg-found].

**Would a GPU digest still be an independent check of a GPU write?** Weaker. The host path's independence is structural: `map_host` → `host_access` → `acquire_access` + `commit_m4(true)` (tessl runtime.rs:606-627, tensor.rs:165-193 [V]) waits for every encoded command *outside* the encoder before the bytes are read. A GPU digest is encoded on the same queue by the same tessl encoder whose ordering/barriers/bindings are the thing the check guards: a dispatch ordered before the decode's writes land, or a binding that reads the wrong buffer, is a false pass with no second observer. It does still hash the real bytes, so it catches the plain accidental write — but hardening §6 (`docs/hardening.md:126`) is written as a host-observed property.

**What v2 (tree hash on the GPU) would buy.** 64 KiB leaves, thousands of threads: ~1–3 ms per digest at 8K, <1 ms at task length [I, hashcat-class ~60–100 GB/s unverified on M5]. Versus CPU after 1a+1b: saves ~2–3 ms/digest at task length (6–9 ms of a ~90 ms post-1a/1b decision ≈ 8–10%) and ~25–30 ms/digest at 8K (~3–4% of ~2.3 s). It is a contract change because (i) the record bytes change, so `StateRecord.digest`, `PINNED_V1`, every ledger `state_digest` and the gpu.rs pins change; (ii) the check moves from host-observed to device-observed (the §6 reading above); (iii) `docs/schema-api.md` and `tests/readonly_slot_isolation.rs` describe what `Ran{state_hash}` means. Human's call, and my recommendation stands: **do not ask now**; revisit only if the measured digest share after 1a+1b is above 5% of a task-length decision.

**Does the embed A/B mean `EmbedPath::Device` is deleted?** Yes. Measured equal-to-slower at three T [V]; the human's rule is "GPU only if faster". Delete it with the serial digest arm once the digest A/B row is in — and in the same commit change `parse_args`'s default arms (decision.rs:180, still `embed=host,embed=device`), or the default becomes a parse error. Keep the `Arm` enum only if a digest A/B remains; otherwise the enum, `digest_by`, `DigestPath` go too (replace, don't accumulate).

## 2. Review of the 1a diff — ranked

1. **Retain cap below the product's own state (correctness-of-bound, perf cliff).** `DIGEST_SCRATCH_RETAIN_BYTES = 256 << 20` (model.rs new), but `qd-metal-serve --max-tokens` defaults to 16,384 (serve.rs:88-89) and the backend GPU test uses `max_tokens: 16_384` (gpu.rs:137). A 16K state is ~423 MB: the scratch is dropped after **every** digest and re-faulted on the next (~26K 16-KiB faults + kernel zeroing of 423 MB ≈ tens of ms, three times per decision) [I]. Fix: derive the cap from the configured `max_tokens` (the backend knows it; `Model` knows `cfg`), or drop the cap — one worker thread, one state-bounded scratch, and the GPU already holds a state that size. Fail-first: a GPU-free `PrefixState::nbytes_for(cfg: &ModelConfig, tokens: u32) -> usize` and `assert!(retain_cap(cfg, 16_384) >= nbytes_for(cfg, 16_384))` — fails today.
2. **The pins pin tessl's kernels too, and nothing records which.** The state bytes are kernel output, so `PINNED_V1` is a property of (weights × tessl tree × digest code). The docstring records Lappi `3d68484`, model.rs sha, Cargo.lock sha — not tessl's `TreeState`, and tessl main has 30 dirty paths. Any kernel edit fails `gpu_prefix_state_digest_v1_is_pinned` with "the v1 prefix-state digest changed", which is the wrong first suspect. Fix: record tessl commit + dirty-tree digest (`ledger::TreeState` exists) beside the pins, and make the message say "re-run `gpu_digest_paths_are_bit_identical` first; if it passes, the kernels moved, not the digest". That test is tessl-independent and is the real proof of 1a.
3. **`Cargo.lock` in the worktree is main's dirty lock, byte for byte** (`diff` → identical; +ojas-core, qd-train-metal, clap edges vs `3d68484`) [V]. It is not part of 1a and must not be staged. A `--locked` build on the committed `3d68484` lock is unverified — the Cargo.lock holder's problem, name it.
4. **Fan-out cap of 8: attribution unverified; two caps; not the lever.** The lib.rs doc and the drafted commit message say "the Mac-stability cap the lead set (AUDIT/mac-stability-2026-10-02/report.md)". `rg` over that report, the Fable hardening ruling, `CLAUDE.md` and `tools/mac_heavy.sh` finds `-j 2` / `--test-threads=2` / load ≤ 12 and **no 8-thread cap** [rg-found]. Cite the lead's actual message or delete the sentence. Also `max_workers` is both a parameter and an inner clamp to the constant — keep one (drop the inner clamp; the one caller passes the constant). On throughput, per-buffer sequential SHA means **the largest buffer on the slowest core bounds each round**: 8K is 12 × 16.8 MB → 2 rounds on 8 workers (≈57 ms soft) and ≈56 ms on 18 because an E-core takes a 28-ms buffer at half speed; task length is 18 × ~1 MB → ≈4–5 ms either way. 8 vs 12 vs 18 moves little; say the arithmetic, not the number.
5. **After 1b the copy and the 48 lease acquisitions are the digest.** Hardware SHA on 8 threads over 23 MB ≈ 1–2 ms; the copy (~1–2 ms) plus 48 × (`acquire_access` + `commit_m4(true)` with `drain_cold_recycles`/`wait_all_allocators`, runtime.rs:1590-1625) is of the same order, and at 8K a 221 MB copy ≈ the hash [I]. Removing the copy needs a multi-buffer mapping under one lease in tessl (`access_busy` is one `AtomicBool`) — ojas-held, GAP-TESSL-HOST-LEASE… already recorded. Instrument now: `Instant` splits (map+copy vs hash) printed in `gpu_digest_paths_are_bit_identical`; no `Sample`/ledger schema change.
6. **Duplicate T not refused → metric-key collision.** `parse_list` refuses 0 and empty (decision.rs:148-159) but not `T=512,512`; two `TResult`s then write the same `decision.t512.*` keys into the `BTreeMap`, the second silently overwriting, while `ran_ts == args.ts` still passes. Fail-first: `parse_args(["T=512,512"])` is `Err`.
7. **`bench.rs:204` recomputes "completed" beside `build_row`'s `status`.** Two owners of one rule; after this diff they can disagree (bench.rs does not know `all_ts`). Make bench.rs read `row.status`.
8. **Error classification.** A lease failure ("runtime busy", not a GPU fault) surfaces as `MetalError::Gpu` via `.gpu(..)` and `Worker::note` poisons the worker on any `Gpu` (backend.rs:418-422, dirty). Not reachable in the product today (every mapping is scoped on the worker thread), so LOW — relay to backend.rs's owner as a classification note. `digest_by`'s re-entrancy error as `State` is harmless.
9. **Untested degrade path.** `spawn_scoped(..).ok()` swallowing a failed spawn is correct ("costs speed, never coverage") but untested and silent; name it as untested in the commit. A helper panic reaches `resume_unwind` and kills the worker thread; `submit` then returns `Unavailable("…dropped the job without answering")` (backend.rs:219-221) — fail-closed, fine.
10. **Pin test on other weights panics** (gpu.rs new `assert_eq!(model.weight_hash(), PIN_WEIGHT_HASH)`): it reads as a failure, not "not run". Acceptable for an `#[ignore]` GPU test; say so in the doc comment.
11. **Test runtime.** 5.65 s for the qd-runtime lib in debug is fine. If it grows, `[profile.dev.package.sha2] opt-level = 3` in the workspace `Cargo.toml` (clean, no new dependency) is the lever, not fewer rounds.

Correctness items I checked and found sound: v1 record layout (`digest_v1` vs `digest_serial`: same tag, `tokens` LE, per-buffer tag/len u64/hash) and the oracle hex `a1b6d7a8…` **recomputed independently with hashlib here: matches [V]**; one mapping at a time, dropped before the next; `&[u8]` slices into an owned scratch are `Send` so the scope is sound; `digest()` → `Parallel` means backend.rs changes behaviour on merge without a line changing — intended, but tell its owner; the parse/arm logic (mixed discriminants, twice, trailing space) is right; the status rule `tessl_held && all_ts && all_same` and `t_coverage` close the hole where tessl moves and moves back between `before` and `tessl_after` (bench.rs:150-153); the two u32 guards are correct (`checked_mul` in `score`, `saturating_mul` before any alloc in `acts`) and the acts half honestly stated as not fail-first.
