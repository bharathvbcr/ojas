Question. The frame ledger (`bench/results/2026-10-27-frame-ledger`, 7a4a547) totals only the rows that have an Ojas number: 52 of 167 rows, so each total is a floor. What do the other rows cost on a quiet M5 Pro, measured at the ledger's exact shapes? Measurement only: no kernel, routing or Backend change.

Rows. Derived from `ledger.csv` by taking every row whose f32 status is `missing`, dropping `permute` (Lane A is measuring it in `../ojas-78a`), de-duplicating by (op, shape), and adding the memory-dependent rows at every F (m = 5184 F + 32 = 5216, 10400, 15584, 36320): the `[1,m,256]` linear, the rope `[1,m,8,32]`, the residual_add `[1,m,256]`. The op list that results, with the number of distinct (op, shape) rows: layer_norm 7, channel_layer_norm 6, residual_add 14, broadcast_add 4, broadcast_mul 3, scale 1, gelu_erf 10, relu 7, rope_interleaved 7, conv2d 12, conv_transpose2d 4, interpolate_bilinear 1, linear_bias 19, linear_forward 2, attention 7: 104 rows. Not measured, and why: `permute` (Lane A's); `softmax` (no ledger row names it: SpikeTrack never calls it); `interpolate_bilinear` of `[2,1,288,288]` (the output size is not in the profile: session.rs:525 gives 1152 x 1152, session.rs:589 the video's own height and width); the memory cross-attention rows (already numbered at every F).

Parameters the ledger's shape strings do not carry, taken from the call sites and checked against the shape of the next op in the profile: conv2d stride 1 and padding 0 for 1x1; stride 1 and padding 1 for 3x3, except the four stride-2 padding-1 convs (memory_encoder.rs:96: `[32,1152,1152]`, `[16,576,576]`, `[64,288,288]` inputs; and `[1,256,144,144]x[1024,256,3,3]`, whose successors are the 72 x 72 `[1,1024,72,72]` channel_layer_norm, gelu and 1x1, so it halves 144 to 72); the 7 x 7 depthwise conv has groups 256 and padding 3 (memory_encoder.rs:105); every conv_transpose2d is kernel 2, stride 2 (backbone.rs, mask_decoder.rs:175,178); the interpolation is `[1,32,1008,1008]` to 1152 x 1152 (memory_encoder.rs:90, whose successor is `[1,32,1152,1152]`); layer_norm eps 1e-5 and channel_layer_norm eps 1e-6 (timing does not depend on it). Operands are device-resident, uniform in [-1, 1] (weights in [-0.05, 0.05]), and uploaded once.

Arms and method.
- Every row is its own run of arms: the op, and for a linear row both the f32 `linear_bias_forward` (or `linear_forward`) and the same call under `Autocast` in a bf16 region (casts included, as a model under Autocast pays them); plus the control.
- Control. An f32 `linear_forward` at fc1 (`[5184,1024]x[4736,1024]`) in every row's run, as an arm of that run. It must repeat 6.3 TFLOP/s within 3% (6.11 to 6.49); a run whose control does not is contended and repeated. (The GEMM study measured 6.29, the memory-bound run 6.34.)
- Every arm runs twice per round, once in each of two passes over the arms (the repeat is named with a trailing prime); odd rounds walk the arms in reverse. 5 warm-ups, then 25 timed rounds. Time = wall clock around the call with `Backend::sync` on both sides.
- Statistics: min, p10, median, p90 of the 25 samples per arm and per repeat, in milliseconds; bytes = the op's inputs read and its output written (4 bytes per element), GB/s at the median.
- Load: the 1-minute load average from `sysctl vm.loadavg`, printed at the start and end of every row attempt and of the whole run.
- A pair is `ok` when |median(A) - median(A')| <= the larger p90 - p10 of the two, else `NOISY`.
- A row attempt is clean when load at its start and end is at most 6.0, the control repeats 6.3 TFLOP/s within 3%, and no pair of the attempt is NOISY. A row that is not clean is repeated, up to 3 attempts; every attempt stays in `bench-output.txt`. A row with no clean attempt contributes no number to the ledger and stays `missing` with that reason.
- Operation refused by the backend at a shape (the example panics with the error): the row stays `missing` with the error as the reason, and the run continues with the rows after it.

What goes into the ledger. For a clean row the per-call figure is the median of arm A (not A'). A linear row's f32 column is the f32 arm and its Autocast column is the autocast arm, both the joint `linear_bias_forward` (so the ledger's earlier sum of a GEMM median and a bias-add median is replaced, for the rows measured here, by one measured call); every other op has one number for both columns (Autocast changes nothing outside the linears). The status is `quiet`, the source this directory's `bench-output.txt`. For the memory-dependent linear row, the F = 1, 3, 7 cells are replaced by the exact-m measurements and the F = 2 cell keeps its earlier value (a GEMM-plus-bias sum, status unchanged). The totals are recomputed by the same arithmetic as the ledger's.

What would change a reading: a row whose new per-call median differs from the profile's mean by more than 2x (reported, whichever way); a clean run whose control does not repeat (the run is read as contended, the rows repeated); a pair that is NOISY in every attempt (no number); an op the backend refuses (a gap in the backend, reported).
