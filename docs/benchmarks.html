Same job, different defaults

ojas next to the mainstream frameworks

The mainstream frameworks can be configured toward most of these. In ojas they are the default and cannot be turned off. Nothing here is a benchmark of model quality.

How ojas differs from PyTorch and TensorFlow on determinism, device fallback, memory, language boundary, and overflow checks
Contract PyTorch / TensorFlow ojas
Determinism Opt-in (torch.use_deterministic_algorithms); ops without a deterministic kernel raise Default Numerics::Exact: same bits at 1 to 18 CPU threads
Missing device Optional CPU fallback for unsupported ops (for example PYTORCH_ENABLE_MPS_FALLBACK=1) The load fails with the device error; there is no fallback switch
Memory ceiling Out-of-memory error from the allocator when the device runs out try_reserve refuses against a cap you set, before allocating; nested budgets
Service boundary A Python runtime, usually behind a model server In-process Go through gusset; a panic poisons the handle, not the process
Arithmetic Index and size math is up to each native kernel Checked shape, stride, and offset math; overflow-checks = true in release

The guarantees do not cost the step

One forward, backward, and AdamW step of the torch_ref graph on an Apple M5 Pro, ojas CPU against PyTorch 2.13 CPU with 6 threads. Two separate processes were recorded. The tiny torch step moved between them, so both are shown and no single speedup is claimed. Below it, a block-sized scorecard shows the cases ojas loses.

Where the larger step's time goes

ojas CPU, B=2, T=32, d=64. Section clocks after the register-tiling, RMSNorm/RoPE, and view-reshape work.

Not every kernel wins: a single 512×768×768 linear forward takes 4.35 ms in ojas at 6 threads and 1.23 ms in torch. The full-step results come from fewer allocations and fused passes, not faster GEMM. Commands and both raw tables are in docs/bench-cpu-vs-torch.md.

GPU, direction only

Metal is close, wgpu is not, and the GPU was busy

Against PyTorch 2.13 MPS, ojas’s Metal backend ran a nanolab block forward + backward at 0.92–1.07× torch’s speed across rounds, and the block forward alone at 0.66× in round 5, so torch is faster there. The wgpu backend read 0.47× on the block forward + backward in round 3. In round 3 the GPU read 100% busy from another process and the 10% spread gate failed on every one of the 94 rows, and round 5 flagged every row noisy, so these are directions and not results. A paired run on an idle GPU is the next item on the roadmap. CUDA and HIP have not run a kernel.
