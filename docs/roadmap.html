Roadmap

From a working framework to a measured one

The phase this page used to list has landed: a multi-layer nanolab GPT, a device trainer with Muon and AdamW, checkpoint save and resume, and a Go API that loads real weights, trains, and samples. What is left is proof at full size, speed against PyTorch, and breadth.

Order from docs/pytorch-parity-plan.md: correctness and the framework gap first, then the measured speed gaps, then breadth. That document's lane table still lists work that has since landed; the landed list below is what the source contains, and docs/status.md has the counts.

  1. Landed

    The framework layer and what it stands on

    • ✓The guarantees on the home labs: exact CPU bits, budgets that refuse, an explicit device, a panic that returns to Go, and checked shape math.
    • ✓permute on the tape and a multi-head attention gradcheck (ojas-autograd/tests/multihead.rs). The tape can seed a backward pass and hand back a gradient (backward_seeded, take_grad).
    • ✓Muon NS5 on CPU, Metal, and wgpu, checked against the CPU on wgpu (ojas-wgpu/tests/muon.rs).
    • ✓A refused CPU optimizer step writes nothing (ojas-cpu/tests/optim_atomic.rs). Input copies are charged to the budget.
    • ✓Tiled causal attention: a Metal forward with a FlashAttention-2 style backward up to head dim 128, and tiled FlashAttention-2 on wgpu.
    • ✓A fused linear plus cross-entropy on the trait, in vocabulary chunks, native on CPU, Metal and wgpu.
    • ✓One shape contract for every backend (ojas_core::shapes): the same error whatever the budget holds.
    • ✓Typed host storage, so kernels borrow f32 and u32 slices instead of decoding bytes, with bounded 1 MiB readbacks and 64 KiB checkpoint reads.
    • ✓Metal reports a device fault at the next sync, as wgpu does, and wgpu names the first op that faulted.
    • ✓ojas-model: the nanolab GPT written once, with a Graph trait that the tape and an eager Eval both implement, a Trainer, and a checkpoint directory (model.safetensors, optim.safetensors, state.ojck).
    • ✓The Go API on real weights: LoadModel, NewModel, OpenTrainer, TrainStep, SaveCheckpoint, Resume, a GPT-2 tokenizer, and sampled GenerateIDs, under one process-wide memory ceiling.
    • ✓Seeded temperature, top-k, and top-p sampling, a seeded resumable batch sampler over TokenBin, and BF16 and F16 safetensors.
    • ✓ojas-qwen35: a Qwen3.5 whole training step through tessl on Metal, as a provider outside the Backend trait.
    • ✓ojas-device: probe_system reads memory, core clusters, caches, unified memory and pressure, ResourcePlan::derive turns that into a budget and thread advice, and Go reads it through SystemProfile. It is advice the caller applies: nothing adapts on its own, and a field it cannot read stays Unknown.

  2. Next

    Proof at full size, and honest timings

    The code path exists end to end. What it lacks is a recorded run at the size it was built for, and timings taken when the machine is quiet.

    • 1A full 124M nanolab training run through the Go API, with its command, machine and loss curve recorded. The training target is 12 layers, width 768, 12 heads of 64, vocabulary 50304. CI today runs a tiny spec and a 40 KB fixture.
    • 2The paired GPU benchmark against torch MPS on an otherwise idle GPU. Round 3 ran on a GPU that read 100% busy, so every row failed the spread gate and only direction is verified (docs/bench-gpu-vs-torch.md).
    • 3The rows where ojas is slower than torch, ranked in that document. Metal's per-op fixed cost fell once a sleep poll in tessl's synchronize became a condition-variable wait; bandwidth-bound elementwise ops are the remaining gap.
    • 4A decode path with few dispatches per token, and batched Muon GEMMs.

  3. Then

    Decisions that touch every backend

    These change the Backend trait, so each has to cover CPU, Metal and wgpu before it lands.

    • ·Whether the Qwen3.5 step's ops (gated delta net, head-dim-256 grouped attention, partial RoPE) move into the trait, or stay a Metal-only provider.
    • ·A CUDA backend. A design exists (docs/cuda-backend-scoping.md); no kernel has been written.
    • ·A planner on top of the host probe: choosing a device and batch size from the plan, and stopping before a run that cannot fit. Today there is no router, and the CPU kernels do not yet adopt the recommended GEMM block sizes.
    • ·Training Lappi, a typed decision model, without PyTorch. A Rust trainer over tessl’s Qwen3.5 Metal step is climbing a parity ladder on the Mac and a CUDA provider is started; the GH200 campaign stays on PyTorch and no Lappi model has shipped.

  4. Later

    Breadth

    • ·bf16 compute. Weights can be stored as BF16 and F16. Every backend computes in f32.
    • ·Activation checkpointing, GELU, and ReLU². The activation that runs today is SiLU. Training v1 refuses grouped-query attention; nanolab's default is multi-head.
    • ·CUDA and HIP as backends. Each is a probe behind a feature and returns NotCompiled when the feature is off.
    • ·A tokenizer check past the twenty reference strings against tiktoken.

Distributed training is outside this plan. It has one user in the code this plan was ranked against, and a single device covers that user's other work. Status and limits is the snapshot of today. Contributing lists the six behaviours a change is not allowed to weaken.
