Roadmap

A real model through the public API

The kernels, the tape, and the Go boundary exist. The next phase joins them: a multi-layer, multi-head GPT on the tape, with optimizer state that stays on the device, loaded from a checkpoint, and reached from Go Load, Step, and Generate using the file's weights.

Order from docs/pytorch-parity-plan.md: correctness and the framework gap first, then the measured speed gaps, then breadth. That document's lane table still lists work that has since landed; the landed list below is what the source contains.

  1. Landed

    The engine underneath the next phase

    • ✓The guarantees on the home labs: exact CPU bits, budgets that refuse, an explicit device, a panic that returns to Go, and checked shape math.
    • ✓permute on the tape and a multi-head attention gradcheck (ojas-autograd/tests/multihead.rs).
    • ✓Muon NS5 on CPU, Metal, and wgpu, checked against the CPU on wgpu (ojas-wgpu/tests/muon.rs).
    • ✓A refused CPU optimizer step writes nothing (ojas-cpu/tests/optim_atomic.rs). Input copies are charged to the budget.
    • ✓CpuGpt runs the nanolab attention block for inference: RMSNorm, QK-norm, half-split RoPE, grouped-query attention, the per-head gate, the value residual, and SwiGLU (ojas-infer/src/gpt.rs).
    • ✓Seeded temperature, top-k, and top-p sampling, and a seeded batch sampler over TokenBin. Safetensors accepts BF16 and F16.
    • ✓A non-finite gradient fails gradients_match. An all-NaN infer output measures as infinite error in the parity test, where it used to measure as zero.

  2. Next

    The framework layer

    This is the phase that makes the public API train and serve. It depends on the layout work, which has landed.

    • 1Load reads the weights out of the safetensors file. Today it checks the header and counts tensors.
    • 2Step trains those weights and writes the result back. Today it runs cross-entropy on the caller's payload and updates a one-element parameter.
    • 3Generate decodes with the loaded model. Today greedy decode is a fixed two-token demonstration.
    • 4A multi-layer, multi-head GPT on Tape, with optimizer state that stays on the device and a checkpoint round trip.

    The training target is the 124M nanolab default: 12 layers, width 768, 12 heads of 64, vocabulary 50304. The executing Metal training step is still one block at width 128, two heads, sequence at most 16, vocabulary at most 128 (ojas-metal/src/gpu.rs).

  3. Then

    The measured speed gaps

    From the same plan, in its recorded order. GEMM itself is left alone: the plan's own comparison put tessl bf16 against torch MPS at a geomean of 1.03×.

    1. Flash-style attention forward and backward, without materializing the full score matrix.
    2. Metal attention backward. One loaded run at B4 H8 T2048 D64 took 306 ms against 60 ms for torch MPS. That run was single-shot and under load (docs/bench-cpu-vs-torch.md).
    3. Metal head dim above 64. The kernel returns UnsupportedHeadDim past 64. wgpu allows 128.
    4. A one-pass gradient norm, fused linear plus cross-entropy, fused elementwise chains, and batched Muon GEMMs.
    5. A decode path with few dispatches per token.
    6. A paired, interleaved harness of ojas Metal and wgpu against torch MPS at nanolab shapes, min of N, taken when the GPU is otherwise idle.

  4. Later

    Breadth

    • ·bf16 compute. Weights can be stored as BF16 and F16. Every backend computes in f32.
    • ·Activation checkpointing, GELU, and ReLU². The activation that runs today is SiLU.
    • ·CUDA and HIP as backends. Each is a probe behind a feature and returns NotCompiled when the feature is off.
    • ·A tokenizer check past the twenty reference strings against tiktoken.

Distributed training is outside this plan. It has one user in the code this plan was ranked against, and a single device covers that user's other work. Status and limits is the snapshot of today. Contributing lists the six behaviours a change is not allowed to weaken.
