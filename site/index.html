Deterministic Rust AI Engine • In-process from Go

Same inputs.
Same bits. Every run.

ojas is a deep learning engine in safe Rust whose failure modes are part of the contract: results that do not depend on thread count, memory that is refused before it is allocated, devices that never silently become the CPU, and engine panics that come back to Go as errors.

An engine panic is an error, not an exit

            

              The Go package calls Rust in-process through gusset. A panic in the engine is caught on the worker and comes back as gusset.ErrPanic. The handle is poisoned, so torn state is never reused, and Close gets you a clean engine. Your Go service keeps serving the whole time.

An unguarded Rust panic

                
Since Rust 1.81, a panic that unwinds out of an extern "C" function aborts. In a cgo binary that is the whole Go process, with every in-flight request.

              

              

                
With ojas

                
One call fails with an error you can match with errors.Is. Sessions loaded before the panic are dropped, so no torn state is reused.

              

            

          

        

      


      
      

        

          

            
Shape math that cannot wrap

            

              A shape from a checkpoint header or an API request is untrusted input. An unchecked multiply can wrap a huge shape to a tiny buffer, and the first write lands outside it. ojas computes element and byte counts with checked_mul, and release builds keep overflow-checks = true.

        What runs today
        
From a safetensors file to a sampled token

        
The guarantees above hold on a real path, not only in the labs. A Go program loads a nanolab GPT, trains it on a token bin, checkpoints it, and samples from it, all in process. Every step below is in the source and covered by the test suites; no full 124M training run is recorded yet, so CI uses a tiny spec and a 40 KB fixture.

      

      

        

          
1 · Model

          
The nanolab GPT, written once

          
ojas-model holds the spec, the state_dict names (torch exports load unchanged), an order-independent init and the block. One block definition runs two ways: recorded on the autograd tape to train, eagerly to decode.

        

        

          
2 · Trainer

          
Muon and AdamW on the device

          
Hidden matrices train with Muon NS5, the embedding and vectors with AdamW, with gradient clipping and a cosine or WSD schedule. A step that hits a NaN commits nothing, and a checkpoint directory is written beside the old one and swapped in whole.

        

        

          
3 · Go API

          
Paths and ids in, losses out

          
LoadModel, OpenTrainer, TrainStep, SaveCheckpoint, Resume, a GPT-2 tokenizer and GenerateIDs. Weights never cross the boundary, and a step reads back only its loss. See the Go API.

        

        

          
4 · Devices

          
CPU, Metal and wgpu

          
Every Backend op runs on all three and is checked against the CPU. Ask for a GPU that will not open and you get an error, never a CPU model. All open models share one memory ceiling, 1 GiB unless you raise it.

        

      

    

  


  

    

      

        Your machine
        
Reads the machine, then plans or refuses

        
A long run that dies at hour three because the memory was never there is a design failure, not bad luck. ojas-device probes the host and turns it into a plan. A field it cannot read stays Unknown and is never guessed. The plan is advice the caller applies: nothing in ojas changes your settings on its own yet, and a request that does not fit is an error before the work starts.

      

      

        

          
1 · Probe

          
What this host actually is

          
probe_system() reads memory (the tightest cgroup limit up the tree, and the working set rather than page cache), CPU core clusters, L1, L2 and L3 sizes, page size, whether memory is unified, and memory pressure. Each field fails alone to Unknown. On an M5 Pro it sees 6 “Super” plus 12 “Performance” cores and no reported L3.

        

        

          
2 · Plan

          
A budget and thread advice

          
ResourcePlan::derive cuts your budget to what is available and advises threads. An opt-in copy-bandwidth probe measured 120.8 GB/s on one thread and 409.9 GB/s on 18 here, so it advised 4 memory-bound threads. On unified memory it sets shared_budget, so CPU and GPU charge one budget instead of each assuming the whole RAM.

        

        

          
3 · Refuse

          
Stop at the start, not mid-run

          
Budgets refuse with the requested, cap and live bytes. Every open model sits under one process ceiling, 1 GiB by default. In the Qwen3.5 provider, a 2B staging step once reached 52.44 GB against a 51.54 GB working-set limit and faulted in 4 of 4 runs. It now recycles first, then refuses on the measured allocation before any GPU work.

        

        

          
4 · From Go

          
You choose the numbers

          
SystemProfile(ctx, budget, measureBandwidth) returns a versioned record. A Go host then calls SetMemoryCeiling and sets LoadOptions.Threads itself. Defaults are unchanged on purpose: ojas prefers explicit to inferred, so adapting is opt-in. See features.

        

      

      

        
Not yet

        
There is no automatic router: nothing picks a device or shrinks a batch for you. The GEMM block sizes the probe recommends are not adopted by the CPU kernels. The probe was run on one Apple M5 Pro; it is compile-checked for Linux and Windows but has not run there. On unified memory the budget counts logical bytes, and Metal can hold up to twice that, so leave headroom. The record is in docs/adaptive-resources.md.

        Why ojas
        
A wrong answer is worse than an error

        

          Most ML bugs that cost days do not crash. A kernel clamps a dimension, a counter wraps, a NaN slips past a check, a test skips when the GPU is missing, and training carries on producing numbers. ojas makes each of those a typed error at the point it happens.
        

      


      

        

          

            
Reproducible by default

            
The default Numerics::Exact tier gives the same bits at 1 to 18 threads. A loss curve that moves after a change moved because of the change, not the scheduler.

          

          

            
Failure is typed and early

            
CapacityExceeded, UnsupportedHeadDim, NonFinite and OutOfRange are values, not log lines. On the CPU an AdamW step with a bad input is refused before it writes anything. wgpu reports a NaN at the next sync and names the op that produced it.

          

          

            
The device you asked for

            
A Metal or wgpu session either opens that device or fails to load. A backend that has not implemented an upload returns Unsupported instead of computing on the host.

          

          

            
It reads the machine first

            
probe_system reports memory, cores, caches and whether memory is unified, and a plan cuts your budget to fit. A field it cannot read stays Unknown. The point is a refusal at the start of a run, not a crash at hour three.

          

          

            
Embeds in a Go service

            
No Python runtime and no model server. The engine links into the Go binary through gusset, and an engine panic is an error value, not a dead process.

          

          

            
Every claim is a test

            
Each guarantee is backed by a test in the repo, and the home labs name the file. Most library crates use #![forbid(unsafe_code)]; ojas-simd, ojas-device, ojas-qwen35 and the gusset engine crate are exceptions, and the CUDA and HIP crates forbid it only while their feature is off. Release builds keep overflow checks on.

          

          

            
Numbers you can recheck

            
Timings come from recorded runs, including the ones where PyTorch wins. There is no headline speedup, because the measurements do not support one.

          

        


        

          
From the author

          
Why I built ojas

          

            
I write training and inference engines for my own research: tessl and metal-native on Metal, gemma-metal, BINN, Lappi, and gusset for calling Rust from Go. When I audited them side by side, the worst bugs had the same shape in every repo. The code kept running and returned a wrong answer.

            
    
              
  • ›An attention backward kernel clamped head dim to 64, dropping the rest of every head without a word.
    • 
              
  • ›An AdamW step counter could wrap from u64::MAX to 0 and turn the bias correction non-finite.
    • 
              
  • ›NaN gradients passed clipping and stayed in the Adam moments.
    • 
              
  • ›A parity harness took the max error with fold(0, max), which drops NaN, so a kernel that returned NaN passed.
    • 
              
  • ›39 GPU tests returned early when no device opened, so CI went green with no kernel run.
    • 
              
  • ›Panics crossed a C ABI with no catch_unwind and took the host process down.
    • 
            

            
PyTorch was not the way out for this work. In my own runs MPS was 3.8× slower than the CPU on a 172K-parameter model, its allocator cache reached 30 GiB with 16 GiB live, and there is no peak-memory API to catch that early.

            
ojas is where each of those fixes lives once, as a refusal with a test behind it, instead of a patch repeated in six repositories.

          

          
Sources: docs/audit.md for the defects and their ojas defenses, docs/pytorch-parity-plan.md section 3 for the PyTorch measurements.

        Questions
        
What ojas guarantees

      

      

        

          
            What does bit-identical determinism mean?
            +
          
          

            In the default Numerics::Exact tier, the same inputs produce the same IEEE-754 bits at every CPU thread count. Threads split outputs, and each reduction runs in ascending order without FMA. ojas-cpu/tests/exact_golden.rs pins output digests at 1, 2, 3, 7, 16, and 18 threads. The CPU reference is checked against PyTorch 2.13, with a measured loss error of 2.38e-7 on the published step. The Fast tier trades this for speed and says so in its name.
          

        

        

          
            What happens when an allocation exceeds the memory budget?
            +
          
          

            Budget::try_reserve() returns Err(OjasError::CapacityExceeded) with the requested bytes, the cap, and the live bytes. It does not clamp the request, grow the ceiling, touch the allocator, or abort the process.
          

        

        

          
            How does a Go service call the engine?
            +
          
          

            The Go package talks to the Rust engine in-process through gusset. There is no separate model server and no JSON hop for the step. A panic in the engine comes back as gusset.ErrPanic, later calls return gusset.ErrPoisoned, and Close resets the engine.
          

        

        

          
            Which devices does ojas actually run on?
            +
          
          

            The CPU backend is the bit-identical reference. Apple Silicon uses Metal 4 through tessl. Portable GPU shaders are WGSL on WebGPU. NVIDIA CUDA and AMD HIP are behind feature flags. If the requested device is missing, the load returns an error instead of a session that silently runs on the CPU.
          

        

        

          
            Is ojas published on crates.io?
            +
          
          

            No. The Rust workspace sets publish = false, and there is no crate named ojas. Clone the repository and build a member such as ojas-core. The Go module path is github.com/bharathvbcr/ojas/go.
          

        

        

          
            Are overflow checks on in release builds?
            +
          
          

            Yes. The workspace release profile sets overflow-checks = true and panic = "unwind". Shape, stride, and byte-offset math uses checked_mul and checked_add and returns OjasError::OutOfRange instead of wrapping.
          

        

      

    

  


  


    

  

    

      

        Same job, different defaults
        
ojas next to the mainstream frameworks

        
The mainstream frameworks can be configured toward most of these. In ojas they are the default and cannot be turned off. Nothing here is a benchmark of model quality.

      

      

        

          How ojas differs from PyTorch and TensorFlow on determinism, device fallback, memory, language boundary, and overflow checks
          
            

              Contract
              PyTorch / TensorFlow
              ojas
            

          
          
            

              Determinism
              Opt-in (torch.use_deterministic_algorithms); ops without a deterministic kernel raise
              Default Numerics::Exact: same bits at 1 to 18 CPU threads
            

            

              Missing device
              Optional CPU fallback for unsupported ops (for example PYTORCH_ENABLE_MPS_FALLBACK=1)
              The load fails with the device error; there is no fallback switch
            

            

              Memory ceiling
              Out-of-memory error from the allocator when the device runs out
              try_reserve refuses against a cap you set, before allocating; nested budgets
            

            

              Service boundary
              A Python runtime, usually behind a model server
              In-process Go through gusset; a panic poisons the handle, not the process
            

            

              Arithmetic
              Index and size math is up to each native kernel
              Checked shape, stride, and offset math; overflow-checks = true in release

        GPU, direction only
        
Metal is close, wgpu is not, and the GPU was busy

        
Against PyTorch 2.13 MPS, ojas’s Metal backend ran a nanolab block forward + backward at 0.92–1.07× torch’s speed across rounds, and the block forward alone at 0.66× in round 5, so torch is faster there. The wgpu backend read 0.47× on the block forward + backward in round 3. In round 3 the GPU read 100% busy from another process and the 10% spread gate failed on every one of the 94 rows, and round 5 flagged every row noisy, so these are directions and not results. A paired run on an idle GPU is the next item on the roadmap. CUDA and HIP have not run a kernel.

      Roadmap
      
From a working framework to a measured one

      
The phase this page used to list has landed: a multi-layer nanolab GPT, a device trainer with Muon and AdamW, checkpoint save and resume, and a Go API that loads real weights, trains, and samples. What is left is proof at full size, speed against PyTorch, and breadth.

      
Order from docs/pytorch-parity-plan.md: correctness and the framework gap first, then the measured speed gaps, then breadth. That document's lane table still lists work that has since landed; the landed list below is what the source contains, and docs/status.md has the counts.

    • 3The rows where ojas is slower than torch, ranked in that document. Metal's per-op fixed cost fell once a sleep poll in tessl's synchronize became a condition-variable wait; bandwidth-bound elementwise ops are the remaining gap.
      • 
            
    • 4A decode path with few dispatches per token, and batched Muon GEMMs.

    Decisions that touch every backend
    
          
    These change the Backend trait, so each has to cover CPU, Metal and wgpu before it lands.
    
          
      
            
    • ·Whether the Qwen3.5 step's ops (gated delta net, head-dim-256 grouped attention, partial RoPE) move into the trait, or stay a Metal-only provider.
      • 
            
    • ·A CUDA backend. A design exists (docs/cuda-backend-scoping.md); no kernel has been written.
      • 
            
    • ·A planner on top of the host probe: choosing a device and batch size from the plan, and stopping before a run that cannot fit. Today there is no router, and the CPU kernels do not yet adopt the recommended GEMM block sizes.
      • 
            
    • ·Training Lappi, a typed decision model, without PyTorch. A Rust trainer over tessl’s Qwen3.5 Metal step is climbing a parity ladder on the Mac and a CUDA provider is started; the GH200 campaign stays on PyTorch and no Lappi model has shipped.

  4. 
          
    Later
    
          
    Breadth

Core concepts

            

              

                
Tensors are views

                
A Tensor is a shape, strides, a dtype, and an explicit byte_offset into shared storage: an Arc<Vec<u8>> on the host or a backend's buffer on a device. narrow and view change the offset and shape without copying. Writing in place needs sole ownership of the storage, so a tensor shared with a view cannot be modified behind its back.

                
byte address of index i = byte_offset + Σₖ iₖ · strides[k] · dtype.size_bytes()

                
Host accessors such as to_f32_vec refuse a device tensor. to_host copies back explicitly and is counted by device_readbacks().

              

              

                
Budgets refuse, they never clamp

                
Budget::new(cap) is an atomic byte counter. try_reserve returns a reservation or CapacityExceeded { requested, cap, live }. Budget::child(cap) charges its parent first and releases that charge if the child refuses. Backends charge outputs and scratch to the budget they were built with. Allocations outside it, such as vec!, format! and thread::spawn, can still abort on real memory exhaustion.

              

              

                
Two numerics tiers

                

                  

                    
Numerics::Exact (opt-in)

                    
Packed GEMM on a persistent thread pool. Threads split outputs, and every sum runs in ascending order without FMA, so results are bit-identical at any thread count. Select it with .with_numerics(Numerics::Exact). The Go API has no selector except the CPU-only LoadOptions.Numerics.

                  

                  

                    
Numerics::Fast (default)

                    
FMA is allowed and reductions may be reordered. On macOS, products of at least 213 multiply-adds go to Accelerate cblas_sgemm; smaller ones use the SIMD tile. Metal and wgpu are Fast.

                  

                

              

              

                
One Backend trait

                
ojas_core::Backend is implemented by CpuBackend, MetalBackend and WgpuBackend. Each op has a forward and, where it trains, a backward:

                

                  embedding
                  linear
                  rms_norm
                  rope_half_split
                  rms_qk_norm
                  causal_sdpa
                  per_head_sigmoid_gate
                  value_residual_blend
                  silu
                  mul
                  residual_add
                  cross_entropy_mean
                  permute
                  clip_grad_norm
                  adamw_step
                  muon_ns5_step
                  upload / download
                

                
The trait's default upload and permute return Unsupported, so a backend that has not implemented them refuses the call instead of computing on the host.

              

              

                
Errors: OjasError

                

                  
                    
VariantReturned when

                  
                  
                    
ShapeShapes or ranks do not fit the op.

                    
DtypeThe tensor's dtype is not the one the op expects.

                    
OutOfRangeChecked arithmetic overflowed, an index or view ran past its storage, or a step counter reached u64::MAX.

                    
NonFiniteA NaN or infinity reached a value that would be applied or returned: logits, gradient norm, optimizer update.

                    
UnsupportedHeadDimThe backend's attention kernel cannot run that head dim (Metal and wgpu above 128).

                    
CapacityExceededA reservation would pass the budget cap, or the allocator refused.

                    
UnsupportedThis backend cannot run this op. There is no CPU fallback.

                    
PlacementThe tensor is on a different device than the call needs. Nothing is copied implicitly.

                    
BackendA device or driver call failed; the detail names it.

                    
PoisonedThe Metal device thread caught a panic earlier and refuses later commands.

                  
                

              

            

          



            
Feature reference

            
What each part does today, with its limits. A limit is a refusal, never a clamp.

            

              

                
Tensors & dtypes

                
    
                  
  • DTypes F32, Bf16, F16, U32. Compute is f32 on every backend.
    • 
                  
  • Zero-copy narrow and view; permute up to rank 8.
    • 
                  
  • Shape, stride and byte math is checked_mul/checked_add.
    • 
                

              

              

                
Autograd

                
    
                  
  • Tape records embedding, linear, RMSNorm, QK-norm, RoPE, causal attention, the per-head gate, value residual, SiLU, mul, add, reshape, permute and cross-entropy, and walks backward from any node or from a seed you supply. A fused linear plus cross-entropy keeps the full logits off the tape.
    • 
                  
  • Gradients are checked against f64 central differences (central_diff, gradients_match).
    • 
                  
  • On Metal and wgpu, leaves are uploaded once and intermediates stay on the device.
    • 
                

              

              

                
Model & trainer

                
    
                  
  • ojas-model holds the nanolab GPT once: ModelSpec (the 124M default and a tiny CI spec), nanolab state_dict names, and an init where each parameter has its own counter RNG, so order never matters.
    • 
                  
  • One block over a Graph trait, run by the tape to train and by Eval to decode.
    • 
                  
  • Trainer splits parameters by rule: hidden matrices to Muon, the embedding and vectors to AdamW. Its checkpoint directory is written beside the old one and swapped in whole.
    • 
                  
  • Training v1 refuses grouped-query attention; nanolab's default is multi-head.
    • 
                

              

              

                
Go API

                
    
                  
  • Load or create a model, open a trainer over a token bin, step it, save, resume, tokenize and sample, all in process. See the Go API reference.
    • 
                  
  • Weights never cross the boundary, and a step reads back only its loss.
    • 
                  
  • Every model's byte budget is a child of one process-wide ceiling, 1 GiB by default.
    • 
                  
  • Failures are typed: ErrCapacity, ErrNonFinite, ErrDeviceLost, ErrBusy, ErrPoisoned, ErrPressure.
    • 
                

              

              

                
Qwen3.5 provider

                
    
                  
  • ojas-qwen35 runs a Qwen3.5 whole training step through tessl's Metal kernels. It is a provider, not a Backend, and is empty off macOS.
    • 
                  
  • Its config reader refuses every field the step does not implement, by name, before tessl reads a byte.
    • 
                  
  • Per-parameter learning-rate scales and weight decays come from the caller's rules, with no built-in exclusions.
    • 
                

              

              

                
Backends

                
    
                  
  • CPU: 1 to 256 threads, Exact or Fast. NEON and AVX2+FMA kernels in ojas-simd.
    • 
                  
  • Metal: every Backend op, device-resident, through tessl, with tiled causal attention. Head dim at most 128.
    • 
                  
  • wgpu: WGSL compute, device-resident, within 1e-4 relative of CPU. Head dim at most 128.
    • 
                  
  • CUDA / HIP: one affine kernel and a copy probe behind features; not backends.
    • 
                

              

              

                
Optimizers

                
    
                  
  • adamw_step: PyTorch single-tensor order, decay first, eps 1e-8 outside the square root.
    • 
                  
  • muon_ns5_step: five Newton–Schulz iterations in f32 on CPU, Metal and wgpu.
    • 
                  
  • clip_grad_norm with eps 1e-6; cosine and WSD schedules; step counter refuses to wrap.
    • 
                  
  • On the CPU a step is all-or-nothing: a refused step leaves every tensor bit-identical.
    • 
                

              

              

                
Inference

                
    
                  
  • argmax_token refuses a non-finite row instead of returning token 0.
    • 
                  
  • sample_token: temperature, top-k, top-p, seeded; temperature 0 is greedy.
    • 
                  
  • CpuGpt with a KvCache and greedy decode, on the CPU.
    • 
                

              

              

                
Data & IO

                
    
                  
  • TokenBin reader and a seeded epoch batch sampler that visits every window once.
    • 
                  
  • GPT-2 BPE, checked against tiktoken on 20 reference strings.
    • 
                  
  • Strict safetensors (F32, BF16, F16, I64, U16), written in a stream so the whole model need not sit on the host, and the Checkpoint v1 codec.
    • 
                

              

            

          



            
Go API reference

            
Package github.com/bharathvbcr/ojas/go. Every call takes a context.Context, and a nil context is an error. Calls run in-process on gusset's worker pool.

            
A model id names a nanolab GPT held on one device by the Rust engine. Go sends paths, token ids and options; weights never cross the boundary. The usual order is SetModelRoot, LoadModel (or NewModel), OpenTrainer, a loop of TrainStep, SaveCheckpoint, and GenerateIDs. Every path is relative to the model root. The worker pool defaults to 1; SetPoolSize changes it before the first call.

            

              

                
                  
FunctionBehavior

                
                
                  
SetModelRoot(ctx, dir)Directory that relative paths resolve under. Absolute paths and paths that leave the root are refused.

                  
SetMemoryCeiling(ctx, bytes)Replaces the process-wide byte ceiling that every model's budget draws from (1 GiB by default, or the machine's hard limit if smaller). Refused for 0, if above physical RAM or cgroup limit, and while any model is open: Free every id or Close first. A 124M training session needs several GiB, so raise it before loading.

                  
SystemProfile(ctx, budget, measureBandwidth)Read-only. Returns the host profile and a plan for your budget: memory, core clusters, caches, whether memory is unified, pressure, and thread advice (a bandwidth measurement runs only when asked, takes about half a second and is not cancellable). A field the engine could not read is flagged unknown. It changes nothing: you pass what you choose to SetMemoryCeiling and LoadOptions.Threads. BudgetBytes counts logical bytes, so leave headroom on a Metal model.

                  
LoadModel(ctx, path, LoadOptions)Reads a nanolab safetensors file (state_dict names, spec in __metadata__["ojas.spec"]), checks every tensor against the spec before keeping any, preflights parameter bytes against the session budget, and uploads the weights to opts.Device. DeviceCPU, DeviceCPUParallel (Threads 1 to MaxCPUThreads = 256), DeviceCPUAuto (threads sized automatically to the machine's thread ceiling), DeviceMetal, DeviceWgpu. A device that cannot open is the load's error. BudgetBytes caps the model, its trainer and every call on it (0 means 1 GiB). Numerics is CPU only.

                  
NewModel(ctx, ModelSpec, seed, opts)A fresh nanolab init: each parameter draws from its own counter RNG keyed by the seed and its name.

                  
Inspect(ctx, path)Counts the tensors in a safetensors file from its header alone. No model id is created.

                  
OpenTrainer(ctx, id, TrainConfig)Attaches a trainer at step 0 over a token bin (BinHeaderless or BinFineWeb). NanolabTrainConfig fills nanolab's defaults: Muon 0.025, AdamW 6e-4, clip 1.0, abort on a non-finite value. A model that already trains is refused.

                  
TrainStep(ctx, id)One optimizer step over the next Accum sampled micro-batches. Returns StepResult{Loss, GradNorm, MatrixLR, AdamLR, Step, Tokens}; only the loss is read back. A step that fails before its optimizer commits nothing; one that fails inside it leaves the model ErrPoisoned.

                  
TrainStepTokens(ctx, id, seq, x, y)The same step on caller micro-batches. The sampler's cursor does not move.

                  
SaveCheckpoint(ctx, id, dir)Writes model.safetensors (loadable by LoadModel and torch), optim.safetensors and state.ojck. The directory is written beside dir and swapped in whole, so an error leaves an earlier checkpoint as it was.

                  
Resume(ctx, dir, opts, cfg)A new model id with the saved trainer, continuing the run on opts.Device. cfg must equal the saved config field for field, tokenizer hash included; a mismatch creates nothing.

                  
LoadTokenizer / Tokenize / DetokenizeA GPT-2 byte-level BPE from a Hugging Face vocab.json and merges.txt under the model root. Special tokens encode as plain text. Ids that do not form UTF-8 are an error.

                  
GenerateIDs(ctx, id, prompt, SampleOptions)Continues the prompt with the model's current weights on its device. Temperature 0 is greedy; TopK, TopP, Seed, MaxNewTokens and Stop ids are options. The prompt and new ids must fit MaxSeq, else ErrCapacity before anything runs. Each forward reads back one logit row.

                  
GenerateGreedy(ctx, id, prompt)GenerateIDs with temperature 0 and one new token.

                  
Generate(ctx, id, logits)Argmax of caller logits on the host. It needs a live id but reads no model. A non-finite logit is an error.

                  
Free(ctx, id)Drops a model id. An unknown id, including a second free, is an error. A call already running on the id finishes first.

                  
Close(ctx)Joins the worker pool, drops every model and resets the engine, returning when the join ends or ctx does. If workers are still running after gusset's 30 s join budget, Close returns that error and no second pool is opened.

                
              

            

            

              
Matching errors with errors.Is

              

                
ojas.ErrCapacity a byte budget, the process memory ceiling, the 64-model table, or the model's context length

                
ojas.ErrNonFinite a NaN or infinity; the step committed nothing

                
ojas.ErrDeviceLost the device failed mid-session

                
ojas.ErrBusy another call holds this id (pool size above 1)

                
ojas.ErrPoisoned a trainer left partly updated; Resume from a checkpoint

                
ojas.ErrPressure critical memory pressure refused the call before it started; nothing changed, so back off and retry

                
gusset.ErrPanic the engine panicked during this call

                
gusset.ErrPoisoned a call after a panic, until Close

                
context.Canceled the call's context ended; a cancelled step commits nothing

              

              
The kind comes from the typed Rust error, not from matching message text, and counts only at the start of the engine's message, so a path that spells one never selects it. A cancel that lands after a step's last cancellable op does not stop it; the next result's Step says which happened.

Status & limits

            
ojas today is a hardened kernel set with a framework layer on top: a nanolab GPT, a device trainer, adaptive resource planning, and a Go API that loads, trains, checkpoints and samples it. What it lacks is a recorded run at full size and timings taken on a quiet machine.

            
Counts are from kernel hardening and SIMD vectorization on an Apple M5 Pro, 2026-10-04: 1286 Rust tests passed and 0 failed across workspace crates, the Go suite passed 41 of 41, and clippy -D warnings was clean. docs/status.md has the full records.

            

              

                
Works and is tested

                
    
                  
  • ✓Every Backend op on CPU, Metal and wgpu, with parity tests against the CPU and one shared shape contract.
    • 
                  
  • ✓Multi-head attention on Tape through permute, gradchecked against an f64 forward.
    • 
                  
  • ✓The nanolab GPT in ojas-model: spec, init, the block on the tape and eagerly, a Trainer with Muon and AdamW, and checkpoint save and resume.
    • 
                  
  • ✓The Go API on real weights: LoadModel, OpenTrainer, TrainStep, SaveCheckpoint, Resume, tokenizer and GenerateIDs, tested against a checked-in 40 KB fixture.
    • 
                  
  • ✓The Go boundary: device selection, panic poisoning, typed errors, a process-wide memory ceiling, close and reset.
    • 
                  
  • ✓Metal and wgpu report a device fault at the next sync, naming the first op that faulted.
    • 
                  
  • ✓A tiny training step on the CPU, compared with PyTorch 2.13, and a device-resident one on Metal.
    • 
                

              

              

                
Not built, or not yet measured

                
    
                  
  • –A recorded full 124M nanolab training run. CI trains the tiny spec; docs/status.md records no larger run.
    • 
                  
  • –bf16 compute, activation checkpointing, and GELU or ReLU² activations. Every backend computes in f32; SiLU is the activation that runs.
    • 
                  
  • –Running on NVIDIA or AMD hardware. CUDA is one affine kernel and HIP a copy probe, neither a backend. Builds off macOS are inferred, not run, and gusset refuses Windows.
    • 
                  
  • –The Qwen3.5 step as a backend. ojas-qwen35 is a Metal-only provider over tessl, empty off macOS. Its GPU parity tests are ignored by default; when a session ran seven of them, six passed and the real-model test (gpu_real_2b) faulted at its gradient read-back.
    • 
                

              

            

            

              
Where ojas trails PyTorch

              
On the GPU, ojas is slower than torch MPS on most rows of the paired benchmark. The last round ran on a GPU that read 100% busy throughout, so every row failed its spread gate and only the direction is verified; ojas leads on a few rows, among them clip_grad_norm and attention backward. On the CPU, a single 512×768×768 linear is 4.35 ms against 1.23 ms. The ranked rows are in docs/bench-gpu-vs-torch.md and docs/pytorch-parity-plan.md.

            

          



            
Contributing

            
Six behaviors are frozen. A change that weakens any of them is rejected as an invariant violation, whatever it speeds up.

            
    
              
  1. 1byte_offset is explicit and narrow preserves it.
    2. 
              
  2. 2An unsupported head dim returns UnsupportedHeadDim; it is never clamped.
    3. 
              
  3. 3try_reserve returns CapacityExceeded; a budget never shrinks a request.
    4. 
              
  4. 4next_step refuses u64::MAX; counters never wrap.
    5. 
              
  5. 5Non-finite values return NonFinite and are never applied to weights.
    6. 
              
  6. 6The device is explicit; there is never a silent CPU fallback.
    7. 
            

            

              
Before you send a change

              
    
                
  • A fix ships with a test that fails on the code before the fix.
    • 
                
  • A new failure mode is a typed error with a test, not a log line or a skip. A GPU test fails when its device is missing.
    • 
                
  • Numbers in docs come from a recorded run, with the command and machine.
    •
