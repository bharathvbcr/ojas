Reference / Design and contracts

Decision: ojas owns safetensors IO and checkpoints #

Owner decision, 2026-11-01. The tessl side of this record is tessl/docs/io-ownership.md; the two say the same thing from each repository's side. This is the IO slice of the ownership split in unification-plan.md (phase P8), and it is the first phase of that plan to land.

The decision #

ojas owns safetensors, JSON, and NPY IO and checkpoints. ojas_io::safetensors, ojas_io::json, and ojas_io::npy are the canonical implementations. After phase P8's initial adapter step and the Milestone M2 completion (2026-11-02), tessl holds zero duplicate parsers (src/safetensors.rs, src/json.rs, src/npy.rs, and src/plain.rs were deleted in full, removing 1,645 LOC) and re-exports pub use ojas_io::{npy, safetensors}; directly from tessl/src/lib.rs, while tessl/src/config_json.rs consumes ojas_io::json::{JsonValue, JsonLimits}. This follows the binding direction of 2026-10-31 — ojas is the training framework and owns "checkpoints, IO" — and it reverses, in code, the direction an earlier card had taken.

In the initial P8 step (recorded below for provenance): two safetensors parsers (2,200 lines in ojas-io and 950 in tessl) were converged into one parser plus a 517-line adapter in tessl. In Milestone M2 (2026-11-02), ojas-io absorbed the remaining adapter surface (header_bytes, HeaderEntry/TensorEntry accessors, .npy v1.0/v2.0 reader/writer, and physical-memory default helpers) so that tessl's 517-line adapter and its duplicate json.rs, npy.rs, and plain.rs modules were deleted outright.

The tree did not get smaller, and that is the honest number. tessl lost 368 lines of source net (295 insertions against 663 deletions over three files), and its reader went from 950 lines to a 517-line adapter. ojas-io gained 1,396 insertions against 82 deletions over eight files — src/safetensors.rs is 3,070 lines now and src/open.rs 300 — of which about 385 lines are new tests: tests/tessl_rejection_corpus.rs (246) holds tessl's whole rejection corpus against the reader underneath, tests/header_amplification.rs (101) measures where the budget refuses, and the widen_in_place test (38) moved here with the code it covers. The rest is the eight bounds in the next section. One duplicate parser is gone; what replaced it is the discipline the surviving reader did not have, with tests that fail without it. Trading 950 duplicated lines for a bound reader is the point, not the line count.

Three things are deliberately not shared, and each is a decision rather than an oversight:

  • None means different things. In ojas-io a None payload limit is unbounded: it validates a header without loading the file and reads tensor bytes positioned from disk, so opening a checkpoint larger than memory is a legitimate thing to do, and the read path bounds its allocations fallibly. In tessl None means this machine's physical memory, because its loaders hand whole tensors to host code. That default is tessl policy and lives in tessl's adapter.
  • Sub-byte floats. ojas-io supports F4, F6_E2M3 and F6_E3M2 on a checked path: it sizes them from their bit width and refuses any span that is not bit-exact. tessl declines them, because every path below its reader is written in whole bytes. The refusal is TryFrom<StDtype> for Dtype, so it is enforced by the type at open rather than documented. pub type Dtype = StDtype was rejected, because the alias would put those three variants in tessl's namespace with no gate, so a checkpoint naming one would be opened there instead of refused. (The card also says the alias would break four exhaustive matches in tessl/src/qwen35.rs. Checked on 2026-11-02: it would not — those four match DType, ojas-core's compute dtype, with catch-all arms, and that file never names safetensors::Dtype. The reason to reject the alias is the dropped refusal, not a compile error.)
  • Header amplification. ojas-io budgets the JSON tree as it builds it (8 * input + 64 KiB) and refuses a header that would exceed it; tessl's reader had no such bound. ojas-io is the stricter of the two and stays that way, so tessl can no longer open a header made almost entirely of shape dimensions — above about 8 KiB of dimension text, measured at 4,099 dimensions in ojas-io/tests/header_amplification.rs. No model writes such a header; real tensors have rank 5 at most and the 2B's whole header is about 90 KB. Ratified by the owner on 2026-11-02: keep the bound. This is the one behaviour the change narrows rather than preserves, so it was put to the owner rather than recorded as a detail. Raising the ratio to 32x was tried first and reverted: it broke tests/stream_writer.rs, whose writer refuses layouts the reader would refuse, and amplification is scale-invariant, so the two repositories' tests were asking for contradictory things.

What ojas-io absorbed first, and why the order mattered #

tessl's reader was stricter than ojas-io's in several places. Deduplicating in the other order would have dropped each of those bounds silently, so ojas-io absorbed them first, each with a test that fails against the pre-change code. Four of the eight were anticipated; four were found by reading tessl's suite and by running ojas-qwen35's adversarial cases against the migrated path.

#What was missing in ojas-ioFound by

2A per-read budget check — widening BF16 to f32 asks for twice the declared bytescard
3The limit reaching each shard's reader, so reads through a view are boundedcard
4The limit honoured on a single-file checkpoint (fixed earlier, in 9c5e784)card
5File-identity re-check on every read, so a file rewritten in place is refused instead of read through stale offsetsreading tessl's suite
6A byte cap and a regular-file check on the checkpoint indexdiffing the two open_index bodies
7Order-independent shape overflow: [2^32, 2^32, 0] was refused while [0, 2^32, 2^32] — the same empty tensor — openedreading tessl's checked_numel
8A FIFO named as a shard hung the reader instead of being refusedrunning the 26 adversarial cases

Item 8 is the one that matters most: it is a hang, not a missing bound. SafeTensors::open called File::open and left the regular-file check until after it returned, and opening a FIFO for reading blocks until a writer appears. Migrating the loader onto this reader without fixing it would have turned a refusal into a denial of service on a hostile checkpoint. open::open_regular_file is the one owner of that refusal now.

What became of ft-02256073 #

Re-pointed and kept, not superseded. That card routed ojas-qwen35's sharded loading through tessl's CheckpointView and verified it properly. Its work is merged (4affd09 is an ancestor of main), and its 26-case ojas-qwen35/tests/sharded_checkpoint_adversarial.rs is the acceptance bar this change inherited and passes unchanged, 26/26 — symlink-followed, escaping-shard-name, symlink-loop, dangling-link, oversize-header and FIFO cases included. Not one assertion was edited. What changed is only which reader sits underneath.

Two runs before that did not pass, and both found real defects rather than test drift: the first hung on the FIFO case (item 8), the second failed two cases that assert a refused index names the index file, which ojas-io's open_index had stopped doing.

What this leaves for ft-b5fb19e6 #

That card wants more safetensors dtypes and a sharded index in ojas-io, and the decision above puts it downstream of this change rather than beside it. Of its two items:

  • The sharded index is there and is now bounded. CheckpointView::open_index already read model.safetensors.index.json; what this change added is the per-shard budget beside the cumulative one, the 16 MiB cap on the index text before it is read, the regular-file check on the index itself, and the index file named in its own refusals. A sharded checkpoint is read through ojas-io by ojas-qwen35 today, over the 26 adversarial cases.
  • The dtype list is untouched. StDtype still has the same 22 variants, so whatever ft-b5fb19e6 wants beyond them — and the question of whether tessl's Dtype should follow — is still its own work. This change deliberately did not widen either enum: it moved who owns the parser, not what the format admits.

ojas-oracle keeps its wrapper, and is not a third parser #

The card asked whether ojas-oracle/src/safetensors.rs should re-export this reader instead. It should not, and it was never the third parser the question assumed: at 115 lines it already reads the format through ojas_io::SafeTensors — the header grammar, schema, tiling, dtype widths and positioned reads are all this crate's — and adds only the oracle's fixture policy on top.

That policy is deliberately narrower than the reader's, which is why it is not a re-export:

  • a header cap of 1 MiB, where the reader's is 100 MB, because a fixture's header is a few KiB and the 124M export's is about 25 KiB;
  • its own two-variant StDtype of F32 and I64 only, because that is what the generators write, so a fixture naming any other dtype is a generator bug and is refused by the type rather than read;
  • OjasError::OutOfRange { op: "oracle_fixture", .. } rather than IoError, because the oracle's callers are ojas tests.

A re-export would widen all three, and the fixture generators would lose the check that catches them writing something they did not mean to. So the disposition is keep, for the same reason tessl's adapter is kept: the policy on top is the crate's, the format underneath is not.

The ojas/tessl path cycle survives this #

Removing the safetensors strand does not break the cycle. ojas-qwen35/src/config.rs still uses tessl::qwen35_model::Qwen35Config, tessl::gdn_train::{GDN_TRAIN_DK, GDN_TRAIN_BV}, tessl::qwen35::GDN_KEY_DIM and tessl::attn_train::ATTN_TRAIN_HEAD_DIM to validate a config against the kernels that will run it, and ojas-metal depends on tessl by design. So ojas-qwen35 still path-depends on tessl. Those eleven call sites in config.rs and links = "tessl" in tessl/Cargo.toml were read this pass; the consequence — that an ojas worktree at a second path cannot build, because every crate in one build must point at one tessl path and a worktree gets a lockfile collision and exits 101 — is carried over from the card and from an earlier session's finding, and was not re-run here. What this change removes is one strand of the cycle, not the cycle.

A note for whoever takes the MSRV decision (D2 in the plan): tessl already declared ojas-io as a path dependency before this change and used it nowhere, so no Cargo change and no MSRV ask was needed here. tessl declares rust-version = "1.82" while ojas's workspace floor is 1.97, which is a standing inconsistency this change neither created nor fixed.

How this lands: the ojas half is public; the tessl half is not #

This change spans two repositories and is not landable one at a time. The constraint was found by the CI/MSRV session on 2026-11-02 and is now half satisfied, because ojas was pushed later that night.

  • tessl/src/safetensors.rs:238 calls ojas_io::SafeTensors::from_bytes, which this work added in 3e45c70.
  • As of 2026-11-02, ojas's origin/main is 0300578 and 3e45c70 is an ancestor of it (git merge-base --is-ancestor exits 0), so git grep -c 'fn from_bytes' origin/main -- ojas-io/src now matches three times in ojas-io/src/safetensors.rs. The API the adapter needs is public.
  • tessl's origin/main is still a00521f, ten commits behind. So the half that remains unpushed is the adapter itself, which is the safe order.

An earlier version of this section said origin/main was dac0b5b, 29 commits behind, and that from_bytes matched zero files there. That was true when written and is not now; the paragraph is corrected rather than deleted, because the three-step table below was measured against dac0b5b and only makes sense with its base stated. Local main is four commits ahead of origin/main: three of this work's records, and one fix(metal) commit (28edc3d) belonging to another session.

Two details worth keeping straight, because they are easy to conflate:

  • At tessl main (07c2e23) the CI workflow does not mention ojas at all, so no cargo job there can resolve tessl's manifest today, with or without this change — tessl's path dependencies need ojas on disk. That is the subject of a separate card, not of this one.
  • The OJAS_REF: ${{ inputs.ojas_ref || 'main' }} default lives on that card's branch (fix/ci-ojas-checkout-msrv-floor, 4f51e89:42), mirroring ojas's own TESSL_REF.

An earlier draft of this section said that branch landing is what turns tessl red, which is wrong, and the distinction matters because the wrong version reads as "the CI fix must wait for an ojas push". The sequence is three steps, not two, and the middle one was measured by that card's session in paired worktrees (tessl at 4f51e89 beside ojas at dac0b5b, clean, own target dir) and then on the hosted runner:

That order was met by circumstance rather than by plan — ojas was pushed by another session on the owner's say-so, carrying this work's IO commits with it. This work pushed neither repository itself, and tessl's ten commits are still local.

One thing to weigh before pushing ojas, found while checking the backlog: of the 19 commits in b2dd967..main, five are another session's — 7087da0 (to_host on a mapped buffer actually waits for the device, which is SharedBuf and Timeline territory, not a docs-only ride-along), 32e4642, c681f92, 8a3df56 and 0300578, written 22:34–22:58 and interleaved with this work's. Pushing ojas main publishes them too. An IO-only split is possible but is a cherry-pick of this work's fourteen commits, not a range.

Each of the eight absorbed bounds has a test that fails against the pre-change code. Three of them were found by a run rather than by reading: the FIFO hang, and the two adversarial cases that assert a refused index names the index file, which this reader's open_index had stopped doing.

tessl/tests/safetensors.rs kept its rejection semantics: of the 52 malformed inputs it covers, 42 keep their exact needle and 10 are the same refusal in different words, each annotated in place with the needle it had, and the sub-byte block gained two inputs rather than losing any. No test was deleted or weakened. One contract was changed deliberately — the header amplification bound — and ojas-io/tests/tessl_rejection_corpus.rs now holds tessl's whole rejection corpus against the reader underneath, so a future ojas-io change cannot quietly widen what a checkpoint may be.

The ignored tessl test worth naming is opens_the_qwen35_2b_checkpoint, which needs the 4.5 GB file from the Hugging Face cache; it was ignored before this change too.

tessl's full suite ran clean, on the fourth attempt: 2,252 passed, 0 failed, 56 ignored over 206 binaries, exit 0. Not from tessl's live checkout, which another session holds mid-rename and which has src/safetensors.rs deleted from its working tree, but from a detached worktree at tessl d42305f placed beside the real ../ojas so the path dependencies resolve, with its own CARGO_TARGET_DIR. It asserts enum Dtype and impl TryFrom<StDtype> are present before testing, so it cannot be a run of that writer's tree.

Three earlier attempts produced no number, each for a different reason — a SIGKILL mid-compile at load 38, a six-second build failure on that rename, and a run that reached 74 of 206 binaries before cargo test abandoned the rest at the first failure. The last of those failures was in this work: tessl's docs_name_real_tools guard rejected its own decision record for naming tests/tessl_rejection_corpus.rs and tests/header_amplification.rs, which are this crate's files, as though they were tessl's. Fixed by qualifying them.

One caveat the run cannot shed: it builds against the live ../ojas, which carries that session's uncommitted additions to ojas-io/src/safetensors.rs (pub type Dtype = StDtype, from_bytes_named). The adapter uses neither, so this is a run of committed tessl against a tree that exists only on this machine.

What is not verified here, and is not claimed to be. cargo fmt --all --check in tessl fails on ten files this change never touched — all wrapped at 100 columns where that repo's rustfmt.toml says 120 — so tessl's fmt CI job is red on main independently of this work. README.md's per-crate test counts come from docs/data/test-runs.json, a single recorded run at 51825fd, so ojas-io still reads 76 passed there; refreshing that means re-running the whole workspace with the command that file records, which this change did not do. An ojas worktree at a second path still cannot build, for the reason in the section above.

Follow-up (2026-11-02, Milestone M2): Complete Retirement of tessl's Adapter and Duplicate Parsers #

In Milestone M2, the remaining 517-line tessl/src/safetensors.rs adapter and tessl's standalone src/json.rs (482 lines), src/npy.rs (599 lines), and src/plain.rs (47 lines) modules were deleted in full (-1,645 lines in tessl/src/):

  1. ojas-io absorbed .npy v1.0/v2.0 and the remaining safetensors surface:
    • ojas-io/src/npy.rs now owns .npy v1.0 and v2.0 reading and writing (read_f32, read_i32, read_u32, write_f32, write_u32, from_bytes, and read_*_with_limit budget enforcement).
    • ojas-io/src/safetensors.rs exposes SafeTensors::header_bytes, HeaderEntry / TensorEntry accessors, Dtype / StDtype aliases, and open_with_limit / from_bytes_named.
  2. Direct re-export in tessl:
    • tessl/src/lib.rs re-exports pub use ojas_io::{npy, safetensors};.
    • tessl/src/config_json.rs parses model configuration files via ojas_io::json::{JsonValue, JsonLimits} (enforcing max depth 64 and structural node budget 8 * len + 64 KiB).
    • ojas-qwen35 imports ojas_io::safetensors::CheckpointView directly with zero tessl::safetensors references.
  3. AdamW scalar deduplication:
    • tessl/src/qwen35_adamw.rs delegates step bias-correction and decoupled weight-decay scalar computation directly to ojas_core::AdamWScalars::new, eliminating the duplicate f64 scalar formula.
